### 1. Existing MFA can be replaced using only a stolen ID token
**Severity:** Blocking  
**File and line:** `app/api/mfa/setup/start/route.ts:7-30`; `app/api/mfa/setup/verify/route.ts:10-93`  
**Failure scenario:** An attacker with a valid bearer token for an MFA-enabled account calls setup/start, receives a new TOTP secret, generates its current code, and calls setup/verify. The route overwrites `mfa_secrets/{uid}` and issues an `mfa_session` cookie without requiring the existing factor or recent reauthentication, thereby taking over MFA and enabling sensitive operations.  
**Fix:** Require recent authentication plus `assertMfaStepUp` before starting or completing setup when MFA is already enabled. Bind the pending setup to a short-lived, single-use server nonce and complete the secret/profile update transactionally.

### 2. Client-supplied “gaps” are included in the signed run as evidence
**Severity:** High  
**File and line:** `app/api/runs/create/route.ts:171-196, 234-263, 281-324`  
**Failure scenario:** A project owner posts `analysis: {"gaps":[{"title":"SAP-certified","severity":"Low","rationale":"No risk","strategy":"None","complexity":"Low"}]}`. Those untrusted fields become `initialWorklist`, which is included in `unsignedRunPayload`, hashed, and HMAC-signed, so arbitrary client claims become part of an apparently server-authoritative immutable run.  
**Fix:** Exclude model/client gaps from the signed payload, or label and store them in a separate non-evidentiary narrative section. Only deterministic findings recomputed from `legacyCode` should enter the signed evidence/worklist.

### 3. Audit-pack creation signs data without validating the underlying run signature
**Severity:** High  
**File and line:** `app/api/audit-pack/create/route.ts:93-111, 164-197`  
**Failure scenario:** If a run document is modified through an Admin SDK script, operational repair, or database compromise—e.g. `cleanCoreScore` changes while `runHash` and `signature` remain unchanged—the route trusts the stored fields and merely checks that `runHash` exists. It then generates and validly signs an audit pack containing the altered score while claiming attachment to the original run hash.  
**Fix:** Reconstruct the canonical signed run payload, recompute `runHash`, and verify the run HMAC with a timing-safe comparison before generating any pack. Refuse export if either check fails.

### 4. Mutable project worklist overrides immutable run evidence in signed audit packs
**Severity:** High  
**File and line:** `app/api/audit-pack/create/route.ts:113-121`; `firestore.rules:134-145`; `lib/audit-pack.ts:353-385, 486-531`  
**Failure scenario:** After a run is created, its owner updates the client-writable project `worklist` to remove high-risk findings or mark entries fully mapped. Audit-pack creation explicitly prefers `projectData.worklist` over `runData.worklist`, and the resulting ADR and provenance files are then server-signed, presenting the edited scope as evidence bound to the immutable run.  
**Fix:** Use `runData.worklist` exclusively for evidentiary sections. If interactive worklist changes must be exported, place them in a separately identified user-attested file and never describe them as immutable run evidence.

### 5. Unsigned, self-constructed packs are returned as successful verification
**Severity:** High  
**File and line:** `lib/audit-pack-verify.ts:142-194`  
**Failure scenario:** Anyone can construct a ZIP with arbitrary files, matching SHA-256 values, `signed: false`, and a matching manifest hash. Verification returns `status: "integrity-only"` but also `success: true`, so callers that rely on the documented success boolean can display a successful verification for a pack with no platform authenticity whatsoever.  
**Fix:** Set `success` to true only for `status === "authentic"`. Expose local checksum consistency through a separate field such as `integrityValid`.

### 6. Consent records accept client-asserted privacy versions and document hashes
**Severity:** Medium  
**File and line:** `app/api/consent/route.ts:35-58`; `lib/consent.ts:41-53`  
**Failure scenario:** An authenticated caller posts `privacyVersion: "future-approved"` and an arbitrary `contentSha256`. The server writes both into the append-only consent event, allowing the immutable audit record to claim acceptance of a privacy document/version that the server never served or verified.  
**Fix:** Derive both versions and the content hash from server-controlled constants or stored document artifacts. Reject body values that do not exactly match those server-known values.

### 7. Tenant-access requests report success when the administrator was never notified
**Severity:** Medium  
**File and line:** `app/api/request-tenant-access/route.ts:213-238, 352-378`  
**Failure scenario:** Resend returns HTTP 500, or `RESEND_API_KEY` is missing in production. The route logs the failure, sets `s4TenantAccessRequested: true`, and returns `{ success: true }`, although no administrator received the approval token and no recoverable `tenant_access_requests` record containing a pending workflow is created.  
**Fix:** Persist a pending request before attempting delivery and return a failure or explicit `notificationSent: false` when delivery fails. A retryable background job should send the notification from the persisted request.

### 8. Administrative email routes claim delivery despite provider failure
**Severity:** Medium  
**File and line:** `app/api/send-approval-email/route.ts:73-105`; `app/api/send-tenant-approval-email/route.ts:173-200`; `app/api/send-tenant-revoke-email/route.ts:145-172`  
**Failure scenario:** Resend responds with 400/500. The welcome route logs the non-OK response and still returns `{ success: true }`; the tenant approval/revoke routes do not inspect `response.ok` at all and log “Success,” causing the admin console to report that a customer was notified when no mail was accepted.  
**Fix:** Check `response.ok` in every route and return an error or an explicit delivery status on rejection. Do not use a success response or success log unless the provider accepted the message.

### 9. Backup recovery codes can be redeemed concurrently more than once
**Severity:** Medium  
**File and line:** `app/api/mfa/verify/route.ts:33-61`  
**Failure scenario:** Two parallel requests submit the same valid backup code. Both read the same `backupCodes` array before either update occurs, both verify successfully, both write the same remaining array, and both receive valid 12-hour MFA session cookies.  
**Fix:** Redeem backup codes inside a Firestore transaction that rereads and removes the matched code atomically. Issue the MFA cookie only after the transaction commits successfully.
