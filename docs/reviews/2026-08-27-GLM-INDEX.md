## What has actually been checked

**Two.** Everything else in the raw files is unverified and must be treated as a
hypothesis until it is reproduced. Two of roughly twenty findings in the Grok
review were wrong, and one of them needed an emulator run to settle; the same
discipline applies here.

### Confirmed and fixed — security #8

> *Account is activated without Terms consent ever being recorded.*

Real, and a defect introduced by the v2.4.2 registration rebuild itself.
`POST /api/account/register` recorded consent where it was given but activated
the account either way, so a client posting `acceptedTerms: false` came out
`approved` with full API access and no `consent_events` row. `assertAccountActive`
would not have caught it: it grandfathers a *missing* acceptance so pre-consent
accounts are not locked out, and only blocks a previously accepted version that
has gone stale.

Fixed in the same release — the route now refuses activation without a consent
record, guarded by `tests/security-compliance.spec.ts`
("registration refuses to activate an account that did not accept the terms").

### Refuted — security #1

> *MFA session cookie is corrupted by its own base64 padding.*

The claim is that `assertMfaSatisfied` parses cookies with `split('=')` and so
truncates a base64 value ending in `=` padding, failing ~75 % of MFA checks at
random. The parser really is naive, but the value never contains a raw `=`:
Next.js serialises cookie values through `cookie.serialize`, which
percent-encodes them (`=` → `%3D`, `+` → `%2B`, `/` → `%2F`), and the reader
calls `decodeURIComponent`. Reproduced directly:

```
raw value       : YWJjZGVmZ2hpamts+/aGVsbG8=
cookie.serialize: mfa_session=YWJjZGVmZ2hpamts%2B%2FaGVsbG8%3D; Path=/; HttpOnly
```

A live request in the test log confirms the same shape. `tests/security-compliance.spec.ts`
exercises the full MFA lifecycle and would be failing three runs in four if this
were real.

## Overlap with the Grok review

`security` #3 and `meta` #1 are both **V9** from `2026-08-26-TRIAGE.md` — the
published fallback signing key. Already known, already recorded as blocked on a
decision rather than on work: removing it breaks
`tests/audit-compliance-v181.spec.ts`, which signs with it and asserts the result
is valid, so CI needs its own `AUDIT_SIGNING_KEY` first. GLM adds one thing worth
noting — it points out the guard is `NODE_ENV === 'production' && !emulator`, so a
preview deployment signs with the committed constant.

`meta` #3 restates **V18** (tests that pass vacuously when the element is absent).

## The shape of the rest

Not a triage — an honest first read, so the volume is not mistaken for a verdict.

- The largest cluster by far is the **fabricated-figure** class this codebase
  already has a guard test for: a board deck computing savings from arbitrary
  multipliers, missing scores rendering as perfect scores, a "Malicious Payload
  Check passed" badge for code that was never scanned, a differential sandbox
  tester reporting a verification it did not run. If even half of these hold,
  `tests/no-fabricated-figures.spec.ts` needs a much wider list.
- Several **engine** findings are concrete and cheap to reproduce — `MODIFY
  ENTITIES` (the canonical RAP statement) reported as a Critical write to a
  standard table called `ENTITIES`, parameterised CDS views parsed into phantom
  table names, `DELETE dbtab WHERE …` silently skipped. Start here; each is one
  ABAP snippet.
- One **public-content** finding is checkable in a minute: the landing page is
  said to hardcode "23,000+ objects" beside the computed catalog count, which is
  now 32,103.
- The **privacy policy** finding deserves its own look regardless of severity: an
  unconditional "not used for training" promise that the whitepaper qualifies.

## Method

The bundler and its exclusion rules live outside the repo (session scratchpad).
It refuses rather than redacts: a pattern hit aborts the whole run before a single
request goes out, because a redaction that misses is worse than a refusal. Worth
committing as `scripts/ai-review.mjs` if this becomes a habit.

One operational note for the next run: GLM 5.3 is a reasoning model. At
`max_tokens: 16000` the first pass spent the entire budget thinking and returned
an empty `content` — 348 seconds and 16k tokens for a header with nothing under
it. It needs `reasoning: { effort: 'low' }` and real headroom for the answer.
