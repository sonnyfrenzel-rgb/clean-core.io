## High

### Privacy policy falsely promises that Gemini never uses submitted code for model training
- **File and line:** `app/datenschutz/page.tsx:69`
- **Failure scenario:** A user supplies a free-tier Gemini API key and uploads proprietary ABAP. The policy tells them that the content “is not used to train Google’s foundational AI models,” but Google’s unpaid-service terms may permit submitted content to be used to improve products and models. The whitepaper itself acknowledges this distinction at `app/whitepaper/page.tsx:86`, so the legal page gives a broader assurance than the application can support.
- **Fix:** State separately which terms apply to the shared platform key and to paid versus free-tier BYOK keys. Do not promise training isolation where it depends on the user’s Google plan and terms.

### Private-edition S/4HANA code is incorrectly described as unable to compile
- **File and line:** `lib/clean-core-guide.ts:255-256`
- **Failure scenario:** An architect evaluating S/4HANA Cloud Private Edition reads that direct standard-table access, application-server files, and unpublished function calls “do not compile” in SAP’s cloud offerings. Classic custom ABAP remains technically possible in Private Edition, even when it violates Clean Core guidance; the statement conflates Public Edition/ABAP Cloud restrictions with all SAP cloud offerings and can lead to an incorrect migration assessment.
- **Fix:** Scope the compilation restriction to ABAP Cloud and S/4HANA Cloud Public Edition. Explain that Private Edition can still run many classic techniques, but they may be unreleased, upgrade-sensitive, or contrary to Clean Core guidance.

### The published “reproducible” analysis time is inherently non-reproducible
- **File and line:** `lib/reference-analysis.ts:130-133`; displayed at `app/reference-analysis/page.tsx:78`
- **Failure scenario:** A visitor sees an exact value such as “Analysis time 7 ms,” downloads the source, and reruns it. Their result differs because the value is wall-clock time on the web server and varies with process warm-up, hardware, and load; ISR may also cache one arbitrary request’s timing. This contradicts the page’s repeated claim that the reader “should see the same numbers.”
- **Fix:** Remove duration from the reproducible headline figures, or label it explicitly as a non-reproducible observation with environment and benchmark methodology. Keep reproducibility claims limited to deterministic outputs such as findings and scores.

## Medium

### Catalog module pages say every listed object has a successor even when rows explicitly support no-path objects
- **File and line:** `app/catalog/module/[area]/page.tsx:67-69`
- **Failure scenario:** `getObjectsByModule()` returns a classified object for which `resolveApi()` has no successor and `hasNoReleasedApiPath()` is true. The table correctly renders “no released path,” while the introductory sentence says all `rows.length` objects “carry a released S/4HANA successor”; metadata at lines 42-43 similarly describes the full count as objects with successors.
- **Fix:** Compute the successor count from `rows.filter(r => r.successor)` and describe the remainder separately, or restrict the module collection to mapped objects consistently.

### The privacy policy omits the supported email/password authentication path
- **File and line:** `app/datenschutz/page.tsx:51-53`
- **Failure scenario:** A user registers with email and password—the application explicitly recognizes `"Email / password"` as an authentication method in `lib/admin-signup-email.ts:37`. The privacy policy says sign-in uses Google Sign-In and only explains collection from a Google account, leaving the actual email/password credential-processing path undisclosed.
- **Fix:** Add Firebase email/password authentication to the policy, including the data processed, purpose, legal basis, and Firebase’s role. Clarify that Google Sign-In is one available authentication method rather than the only one.

### FAQ structured data contains answers that are not visibly presented as the marked-up FAQ
- **File and line:** `app/page.tsx:111-166`
- **Failure scenario:** Crawlers receive a six-question `FAQPage`, including claims such as automatic conversion to CAP/RAP, but the rendered homepage only visibly presents one related `QuickAnswer`; the marked-up questions and answers are not available to users as an FAQ. This violates Google’s FAQ structured-data requirement that marked-up content be visible and risks the markup being ignored or a manual action.
- **Fix:** Render the same FAQ entries visibly from a shared data source, or remove `FAQPage` markup and use structured data matching the content actually shown.

### Sitemap reports every generation time as a content modification
- **File and line:** `app/sitemap.ts:10-13`, `app/sitemap.ts:17-35`
- **Failure scenario:** ISR or a deployment regenerates the sitemap without any page-content change, and all marketing routes receive a new `lastModified: now`. Search engines are therefore told that every listed page changed, even when its content did not, making the freshness signal untrustworthy.
- **Fix:** Use actual content modification dates, source-control/build metadata tied to changed content, or omit `lastModified` where no reliable date exists.
