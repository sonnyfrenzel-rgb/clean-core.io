## High

**1. Trust-chain tests never prove production HMAC signing — and they lock in a public fallback key**  
`tests/audit-compliance-v181.spec.ts` (verify tests), `tests/security-compliance.spec.ts` (audit-pack create), `playwright.config.ts` / `.github/workflows/deploy.yml` validate job.

`/api/export/verify` is asserted to accept a signature built with a key that lives in the repo:

```ts
const signature = crypto.createHmac('sha256', 'dev_audit_signing_key_fallback_clean_core').update(expectedHash).digest('hex');
```

CI never injects `AUDIT_SIGNING_KEY` into the validate build or `npx playwright test` (only `MFA_BACKUP_CODE_PEPPER`, `PILOT_APPROVAL_SECRET`, `S4_ENCRYPTION_KEY`, `GEMINI_API_KEY`). `playwright.config.ts` does not set it either. So the suite only passes if the server still treats that published string as a real HMAC key whenever the env var is unset.

The create-side test does not close the loop: it checks `manifest.signed === true` and `signature.length > 0`, then re-hashes one file. It never calls `verifyAuditPack` or `POST /api/export/verify` on the ZIP that `/api/audit-pack/create` just produced.

Trigger: any environment without `AUDIT_SIGNING_KEY` (local `next dev`, CI, a mis-set Cloud Run service). Anyone can mint a `valid: true` verify result with the key from the test. Setting the real secret in CI would *break* the fallback test, so the suite actively discourages testing the production key. The trust chain can regress to “non-empty signature field” and stay green.

**2. Shell injection on the weekly usage-report workflow**  
`.github/workflows/usage-report.yml`, “Send the report” step.

npx tsx scripts/send-usage-report.ts --apply \
