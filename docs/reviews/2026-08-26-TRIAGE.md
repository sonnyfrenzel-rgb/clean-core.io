## Fixed in v2.4.1

### Blocking — all fixed

**V1 · A rate-limited verification reports a valid pack as forged.**
`QuotaError` carries `.status`; [export/verify:77](../../app/api/export/verify/route.ts#L77)
and [audit-pack/create:179](../../app/api/audit-pack/create/route.ts#L179) test
`.statusCode`. The 429 branch is unreachable, and the outer catch returns
**HTTP 200 `{ valid: false }`**. For a product built on verifiable evidence this
is the most damaging possible failure: the 31st verification in a minute tells an
auditor the signature is bad.

**V2 · The trust chain does not require MFA.**
`assertMfaSatisfied` appears 0× in `runs/create` and `audit-pack/create` (2× in
`gemini`). With `mfaEnabled: true`, a valid Bearer and no MFA cookie, signed runs
and signed packs can still be minted. A stolen ID token is sufficient.

**V3 · MFA is a UI gate on an already-issued session.**
`components/LandingModals.tsx`: Firebase auth completes before the TOTP prompt, no
sign-out on abandonment, and the email path does not wrap the profile `getDoc` in
its own catch — a Firestore error shows "invalid password" while leaving the user
signed in. Same root cause as V2, opposite end.

**V4 · The delivery handover invents figures.**
[delivery/page.tsx:557](../../app/(app)/project/[projectId]/delivery/page.tsx#L557):
`project?.testCases?.length || 10` and `coverageEstimate?.percentage || 92`. With
the fields missing — or `testCases.length === 0`, since 0 is falsy — the handover
screen states **10 automated tests and 92 % coverage** beside a pulsing "Ready for
Deployment". This is the screen a customer photographs for a steering pack.

**V5 · Shell injection in the weekly usage report.**
[usage-report.yml:73](../../.github/workflows/usage-report.yml#L73) interpolates
`${{ inputs.recipient }}` into a `run:` block. That job holds `id-token: write`,
GCP workload identity and `RESEND_API_KEY`.

**V6 · Rules of Hooks violation, crashes on hydration.**
[UserOnboarding.tsx:25](../../components/UserOnboarding.tsx#L25) returns before the
`useEffect` on line 27. Server render returns early (auth is null server-side),
the browser render runs the effect, React throws on the hook-count mismatch.

### High — V7, V8, V10 fixed; V9 open

**V7 · Any non-boolean grants admin.**
[set-admin-claim:41](../../app/api/admin/set-admin-claim/route.ts#L41):
`const grant = isAdmin !== false;` — `{"isAdmin": "false"}` as a string grants the
claim. This path also never calls `logAuditEvent`.

**V8 · Stored S/4 credentials can be sent to a body-supplied URL.**
`const url = body.url ?? stored?.url` alongside
`password = body.password ?? stored?.password`
([test-s4-connection:271](../../app/api/test-s4-connection/route.ts#L271), and the
same shape in three sibling routes). Mitigated in production by
`S4_HOST_ALLOWLIST`, but that is a config value, not a code invariant:
[url-validation:144](../../lib/url-validation.ts#L144) only enforces the allowlist
`if (al.length)`.

**V9 · The published fallback signing key is locked in by the tests.**
`dev_audit_signing_key_fallback_clean_core` appears in three production routes and
is used by `tests/audit-compliance-v181.spec.ts` to mint signatures the suite then
asserts are valid. CI never sets `AUDIT_SIGNING_KEY`, so setting the real secret
would *break* the tests. Production is protected by the deploy guard
(`deploy.yml:148` fails the deploy if the secret is missing), but the fallback
path and the test that depends on it both remain.

**V10 · Google sign-up bypasses the consent checkboxes.**
Email registration is gated on `agreedGDPR && agreedTerms`; the Google button on
the same form calls `handleSignIn`, which never reads them — and still writes
`termsVersionAccepted`.

**V11 · Rules of Hooks violation in `RoutingRationale`.**
[RoutingRationale.tsx:32](../../components/design/RoutingRationale.tsx#L32) returns
before the `useMemo` on line 37. Triggers when a project loads asynchronously and
the route arrives on a later render of the same instance.

### Medium — V12, V13, V17, V19, V20 fixed; V14, V15, V16, V18 open

V9 needs a decision before it can be closed: removing the published fallback
signing key breaks `tests/audit-compliance-v181.spec.ts`, which signs with it and
asserts the result is valid. CI would need its own `AUDIT_SIGNING_KEY`.


- **V12** Transformation HUD shows 100 % whenever no finding requires sign-off, regardless of the project's actual score; `signedOffIds` is component state only and is lost on refresh.
- **V13** `/api/fetch-s4-metadata` does not constrain `servicePath`, unlike its sibling `test-s4-odata-read`.
- **V14** Client can write `termsVersionAccepted` on user create without a `consent_events` row.
- **V15** `run-tests` places the decrypted S/4 password in the sandbox environment when egress enforcement is on, and returns stdout to the client.
- **V16** `NEXT_PUBLIC_USE_FIREBASE_EMULATOR=true` on a non-Cloud-Run deploy disables rate limits, the test sandbox, admin step-up and the seed-route guard.
- **V17** Jira callback reports success without persisting tokens (behind `JIRA_INTEGRATION_ENABLED`).
- **V18** Several E2E tests are wrapped in `if (await x.count() > 0)` and pass when the element they name is absent.
- **V19** `audit-pack.create` writes `'auditMetadata.auditPackExportedAt'` via `set(..., {merge:true})`, which does not interpret dotted paths — the field is never set.
- **V20** README states v2.2 and Node 20; `package.json` is 2.4.0 and `engines.node >= 22.8`. The version drift guard only walks `app/`, `components/`, `lib/`.
