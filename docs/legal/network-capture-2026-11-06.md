## Reading the result (written by hand, 2026-11-06)

- **What production serves is v3.0.20, and the claim was written for 3.0.21.** The two changes that make section 7 true are not on `main`: `77bdc8f7` (23.10.2026, a public header loads the Auth SDK only for a browser holding the first-party signed-in hint) and `2bd52ff9` (05.11.2026, the public pages of the signed-in shell do the same). Both are on `dev`.
- **Cause on production:** every public page with the public header (`components/HeaderAuthButton.tsx` → `lib/auth-subscribe.ts`) loads the Firebase Auth SDK after hydration for every visitor. In the WebKit engine (desktop and the iPhone profile) Auth initialises proactively (`_shouldInitProactively` in `@firebase/auth`): the top document loads `https://apis.google.com/js/api.js` and a `gapi_iframes` script from apis.google.com, then the frame `https://cleancore-491216.firebaseapp.com/__/auth/iframe` (with `iframe.js`), and that frame calls `https://www.googleapis.com/identitytoolkit/v3/relyingparty/getProjectConfig`. Issuing frame per request in "Third-party requests in detail"; WebKit exposes no script-level initiator, and Chromium made no third-party request at all, so no DevTools initiator applies.
- **Chromium desktop** sends nothing to a third party in any step, 9–11 included: there Firebase Auth contacts Google only on a sign-in action. But it **stores** on the device in every engine: the Auth SDK creates the IndexedDB databases `firebaseLocalStorageDb` and `firebase-heartbeat-database` on every page that loaded it — before any sign-in. No cookie, no localStorage/sessionStorage key, no Cache Storage, no service worker in any step.
- **Step 6 is not evidence for `/report`:** `/report` and `/report/de` answer 404 on production (they ship with 3.0.21); the 404 page has no auth header and therefore came out clean. `/terms/de` also answers 404 on production.
- **Not seen in any step or engine:** Google Fonts (fonts are self-hosted under `/_next/static/media/`), gstatic, Firebase App Check / reCAPTCHA, Firebase Installations, Analytics, an error-reporting service, any WebSocket.
- **Comparison run against the dev service (v3.0.21, commit `bae56e93`), same script, same day:** [`network-capture-2026-11-06-dev.md`](./network-capture-2026-11-06-dev.md). There the claim holds: steps 1–8 contact nobody but the first party in all three engines (fresh contexts and journey), and nothing is stored on the device. From step 9 on, WebKit (desktop and iPhone) contacts `apis.google.com`, `cleancore-491216.firebaseapp.com` and `www.googleapis.com`; Chromium desktop contacts no third party; all three engines create the two Firebase IndexedDB databases.
- **Consequence:** the section 7 sentence is accurate for 3.0.21 as on dev, not for the production release of today. Repeat this capture against production once 3.0.21 is live.
