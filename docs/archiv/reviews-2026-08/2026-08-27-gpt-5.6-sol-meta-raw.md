## High

### Dependency install scripts run with Google Cloud OIDC permission
- **Severity:** High
- **File and line:** `.github/workflows/deploy.yml:16-33`
- **Failure scenario:** The workflow grants `id-token: write` globally, so the `validate` job inherits it. If a compromised dependency executes during `npm ci --foreground-scripts`, its install script can request a GitHub OIDC token and, subject to the configured Workload Identity conditions, impersonate the deployment identity even though this job is only intended to validate code.
- **Fix:** Move `id-token: write` into the `deploy` job’s `permissions` block and explicitly give `validate` and `security` only `contents: read`. Avoid foreground dependency scripts unless required and allowlist any packages whose lifecycle scripts are necessary.

### Catalog sync executes dependency scripts while holding repository write credentials
- **Severity:** High
- **File and line:** `.github/workflows/sync-catalog.yml:9-30`
- **Failure scenario:** `actions/checkout` persists the workflow token in Git configuration, the job has `contents: write`, and then runs `npm ci --foreground-scripts`. A compromised lifecycle script can recover the checkout credential and push arbitrary repository changes or tags, bypassing the intended “generated update goes through a PR” boundary.
- **Fix:** Run dependency installation and catalog generation in a read-only job, upload the generated artifact, and let a separate minimal write-capable job create the PR. Also use `persist-credentials: false` wherever shell-executed dependencies do not need Git credentials.

### Delta sync can overwrite writes made after cutover
- **Severity:** High
- **File and line:** `scripts/firestore-delta-sync.ts:88-94`
- **Failure scenario:** The documented procedure runs this after traffic has switched to the target. If a user updates an existing target project after cutover while the source contains a different pre-cutover version, `fingerprint` detects a difference and `tgtRef.set(doc.data())` replaces the newer target document with the older source document, silently losing the user’s post-cutover write.
- **Fix:** Reconcile against an export-time baseline or compare authoritative update/version timestamps and stop on two-sided changes. Never overwrite a differing target document unless it can be proven that only the source changed since the baseline.

### Migration verifier can declare intact projects when most project data was lost
- **Severity:** High
- **File and line:** `scripts/firestore-inventory.ts:94-96`, `scripts/firestore-verify-migration.ts:123-134`
- **Failure scenario:** The inventory records only each project’s ID, owner and name. If migration preserves those fields but drops `analysis`, `solutionDesign`, test artifacts, audit metadata or other project fields, collection counts and the project manifest still match; the verifier exits zero and prints “Every user, project and signed run survived intact.”
- **Fix:** Store and compare a deterministic hash of every complete project document, using canonical handling for Firestore types. Ideally inventory every document and recursively include subcollections rather than making an “intact” claim from selected fields.

### Remote installer becomes a secret-bearing PR writer without a pinned identity
- **Severity:** High
- **File and line:** `.github/workflows/grok-review.yml:39-61`
- **Failure scenario:** The job pipes the current contents of `https://x.ai/cli/install.sh` into a shell and subsequently executes the installed `grok` binary with both `XAI_API_KEY` and a token carrying `pull-requests: write`. If the installer endpoint or its delivery chain is compromised, the installed binary can exfiltrate the API key and alter PR comments or reviews.
- **Fix:** Download a versioned artifact pinned by checksum or vendor signature and verify it before execution. Until that exists, run the installer/tool in an isolated job without secrets or write permissions and pass only a non-sensitive review artifact to a separate commenting job.

## Medium

### The dependency security gate executes a floating package version
- **Severity:** Medium
- **File and line:** `.github/workflows/security-ci.yml:46`
- **Failure scenario:** `npx --yes audit-ci@^7` resolves and executes whatever release currently satisfies `^7`, rather than the reviewed lockfile version. A compromised or faulty newly published 7.x release can fabricate a successful audit or execute arbitrary code in CI without any repository change.
- **Fix:** Add `audit-ci` as an exact-version dev dependency and invoke the lockfile-installed binary with `npx --no-install audit-ci`, or pin a downloaded artifact by digest.

### Full-pipeline testing stage proves only that an always-passing fixture can turn green
- **Severity:** Medium
- **File and line:** `tests/full-pipeline.spec.ts:166-184`, `tests/full-pipeline.spec.ts:285-301`
- **Failure scenario:** Before analysis, the test seeds a test suite containing only `assert.strictEqual(1, 1)` and a test case already marked `Passed`. Stage 4 then runs that fixture and merely checks that some “Passed” text appears, so regressions that stop generated tests from exercising transformed output can still leave the principal six-stage pipeline test green.
- **Fix:** Seed a deterministic but meaningful transformed module and assert its generated test invokes that module with expected input/output, or intercept generation with a controlled response and verify the actual generated suite is executed. Do not preseed the displayed status as `Passed`.

- **File and line:** `tests/analyze-design.spec.ts:37-45`
