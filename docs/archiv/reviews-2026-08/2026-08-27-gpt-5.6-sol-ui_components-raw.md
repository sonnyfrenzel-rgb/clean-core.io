## Blocking

### Stepper is compiled as a Server Component while calling `useRouter`
- **File and line:** `components/Stepper.tsx:3-6`
- **Failure scenario:** Any server-rendered page importing `Stepper` causes Next.js to reject the module because it uses the client-only `useRouter` hook without a `'use client'` directive. The route fails to build or render.
- **Fix:** Add `'use client';` at the top of the file.

## High

### Custom MFA leaves a fully authenticated Firebase session usable before verification
- **File and line:** `components/LandingModals.tsx:178-184`, `components/LandingModals.tsx:245-251`, `components/LandingModals.tsx:357-383`
- **Failure scenario:** A user with MFA enabled supplies the correct password or completes Google authentication. Firebase immediately establishes a live session, after which the UI merely switches to the custom MFA screen. The user can open `/dashboard` in another tab, and components/API calls that trust the Firebase ID token see an authenticated user even though no second factor has been entered.
- **Fix:** Enforce MFA completion server-side through Firebase MFA or a short-lived server-authoritative claim/session that every protected route and API checks. Do not treat the ordinary Firebase ID token created before the second factor as sufficient authentication.

### Failed email registration can leave a live session behind an error message
- **File and line:** `components/LandingModals.tsx:269-347`
- **Failure scenario:** `createUserWithEmailAndPassword` succeeds, but either initial `setDoc` call fails—for example because Firestore is unavailable or rejects the write. The outer catch displays “Error creating account,” but the newly created Firebase user remains signed in and is immediately visible to auth listeners and protected navigation.
- **Fix:** Track whether account creation succeeded and call `signOut(auth)` on every subsequent fatal setup failure before presenting the registration error. Alternatively, move account provisioning into one server-authoritative operation.

### Profile snapshot listeners are never unsubscribed and can overwrite another user’s profile
- **File and line:** `hooks/useUserProfile.ts:111-153`
- **Failure scenario:** The cleanup returned inside the `onAuthStateChanged` callback is ignored by Firebase. After user A signs out and user B signs in within the same app instance, listeners for both `users/A` and `users/B` remain active; a later update to A can call `setProfile(data)` and expose A’s profile, quota, or settings while B is signed in.
- **Fix:** Keep the current profile unsubscribe function in the outer effect, invoke it before attaching a listener for a new auth user, and invoke it again during effect cleanup.

### Target scope panel presents invented percentages as measured results
- **File and line:** `components/analyze/TargetScopeMapping.tsx:52-91`
- **Failure scenario:** For every project, “Cloud Readiness” is shown as `95%` and “Decommission Ratio” as `80%`, regardless of analysis evidence. “Standardization Fit” similarly converts only the labels High/Medium/Low—or even a missing value—into fixed `90%`, `50%`, or `15%`, putting unsupported figures in front of the customer.
- **Fix:** Accept actual engine-produced numeric values with provenance, or display only the qualitative High/Medium/Low labels. If no figure was computed, explicitly say so and omit the percentage bars.

### Missing coverage summary is rendered as a fully supported verdict
- **File and line:** `components/analyze/CoverageVerdict.tsx:20-27`
- **Failure scenario:** If findings are present but `summary` is absent, the component defaults every count to zero and the overall verdict to `fully`; the counters show 0% in every category while the donut center says “Fully Supported.” With zero findings and no summary, it additionally displays “Fully Supported 100%,” although no summary was supplied.
- **Fix:** Treat a missing summary as “not computed” and do not derive percentages or an overall verdict. Only show 100% fully supported when the evidence engine explicitly produced that result.

## Medium

### Evidence sweep never completes when there are zero findings
- **File and line:** `components/analyze/EvidenceSweep.tsx:86-87`
- **Failure scenario:** The parent activates the sweep for clean code whose `sortedFindings` array is empty. The effect returns immediately, never calls `onComplete`, and the UI remains in a scanning state indefinitely, preventing any parent workflow waiting for completion from advancing.
- **Fix:** When active with zero findings, immediately set the scan complete state and call `onComplete` once, respecting reduced-motion behavior if desired.

### File upload failures inside `FileReader.onload` are unhandled and leave the UI stuck
- **File and line:** `components/FileUpload.tsx:30-50`
- **Failure scenario:** A valid file is read successfully, but `addDoc` rejects because of permissions, quota, or network failure. Since the rejection occurs in an async `reader.onload` callback, the surrounding `try/catch` cannot catch it; `uploading` remains true, the input stays disabled, and the user receives no failure message.
- **Fix:** Wrap the body of `reader.onload` in its own `try/catch/finally`, and add `reader.onerror` handling. Reset `uploading` in `finally`.

### Undefined deployment target is reported as “Private Cloud (RISE)”
- **File and line:** `components/design/RoutingRationale.tsx:116-118`
- **Failure scenario:** A legacy or incomplete run has no `s4Deployment`. The conditional treats every value other than `'public'`, including `undefined`, as private cloud and shows a deployment target that was never recorded.
- **Fix:** Handle `'public'`, `'private'`, and missing values separately; render “Not specified” for absent evidence.

### Empty findings are labelled a “Pristine Codebase” without proving that conclusion
- **File and line:** `components/analyze/ConstructFindings.tsx:16-31`
- **Failure scenario:** A caller supplies an empty findings array because evidence is unavailable, parsing failed upstream, or an older run omitted construct evidence. The component asserts “Pristine Codebase Detected” and specifically claims there are no unreleased queries, screen flows, or dynamic targets, even though an empty array alone cannot distinguish “none found” from “not assessed.”
- **Fix:** Pass an explicit completed/assessed status from the evidence engine. Only show the pristine claim after a successful complete scan; otherwise show “construct evidence unavailable/not computed.”
