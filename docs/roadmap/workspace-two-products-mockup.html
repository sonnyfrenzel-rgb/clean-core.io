My workspace

Today's My workspace, critiqued

Read from the code of v3.0.23 (components/workspace/HomeFirstView.tsx, ToolPathStrip.tsx, WorkspaceListReport.tsx, components/MyWorkspaceSwitch.tsx) and rendered from the accepted home mock-up v2.1 that state 1 was built to (docs/roadmap/home-mockup-v2.html). The running app was not started for this (shared :3000).

New account (HomeFirstView) — the first five seconds

  • Business reader: the h1 "See your Z program as a business process" lands. Then a row of seven tools, six of them dashed under "Optional, if you want to re-design it" — the eye reads "the second half is extra". Re-design, half of what the product does, is presented as an afterthought.
  • IT reader: finds the example and the drop area quickly; the map slice that shows what you get sits below the fold at 1440 (it starts at about 730 px) and is drawn by the full bpmn-js renderer.
  • Management reader: nothing says what a decision or a delivery looks like; cost is a chip ("5 free analysis runs") without saying that the six re-design tools cost nothing.
  • Phone: the own-code start begins at about 720 px of 844 — "Upload your own code" is not in the first viewport, the example is.
  • Noise: the tool strip carries seven descriptions before the user has done anything; the lead repeats the h1; "If you want, it then helps you re-design it" is the second sentence that makes Re-design optional.

Returning account (WorkspaceListReport) — the first five seconds

  • One table of eight columns (Project, Lines, Findings, Levels, Rules confirmed, Status, Last change, Actions 232 px). It is honest and complete, and it is an IT screen: a business reader sees counts with no picture of what the program does; a manager sees no portfolio at a glance (how many analysed, in re-design, delivered).
  • Two of the eight columns say "Reading…" first: Levels and Rules are fetched per visible row from /findings (which runs the evidence engine over the source) and /process-states, two projects at a time. Five rows = ten requests in three waves.
  • The product's best picture — the process map — is absent from the list. Projects are rows, not objects.
  • Re-design is invisible as a product: it appears only as a status sentence ("Re-design under way") and a next-step link.
  • Starting something new is "New project" → /admin/new-project, one page more; the example gallery and the sharing card sit below the list, out of sight.
  • A flash: while the profile loads, MyWorkspaceSwitch renders its children — the old dashboard page — and then swaps to the list report. Both are in the route's bundle.

What is good and is kept

  • Plain words, status as text with a dot, no green unless evidenced, numbers that say "not analysed" instead of 0.
  • Example and own code side by side for a new account (AB-14a) — kept in every direction.
  • The own-code handoff (lib/home-start-handoff.ts → own-code start, ADR-042) — kept unchanged.

Data and speed

What My workspace loads today (from the code)

  1. Server: app/(app)/dashboard/layout.tsx computes the demo row and the home map slice once per server process (cached) — cheap after the first request.
  2. Client bundle: page.tsx is a client component (46.7 kB of source with markdown formatters, sanitizer, dialogs) and is in the bundle even though MyWorkspaceSwitch replaces it with WorkspaceListReport (1,068 lines, ~25 cc components, the analysis-run client) for every account in good standing. Heavy part 1.
  3. Waterfall: auth state → profile document → projects query (one query) and the shared-with-me query → per visible row two API calls, two rows at a time. Heavy part 2: /api/projects/:id/findings runs the evidence engine over the source on each first visit of a row.
  4. New account: the map slice loads bpmn-js (NavigatedViewer) through next/dynamic to draw four elements. Heavy part 3 — hundreds of kB of JavaScript for a picture.
  5. Flash: the old dashboard renders while the profile loads, then is swapped (layout shift).

No current next build output was on disk (.next holds only a cache), so no byte figures are claimed; measuring them is step 1 of the build.

The one server-side addition: a project summary

When a run is signed (app/api/runs/create/route.ts) and when the map is saved, the server writes a small project-level summary with the Admin SDK: mapThumb (SVG string, ≤ 4 kB, geometry only, no names, no code), mapSteps, rulesDerived. No account field. Clients may never write it (Firestore rules: deny the keys on client update — rules deploy is manual). A one-off backfill script for existing projects; a project without a summary shows "Map after the next run" in the thumbnail place. It is not part of the signed run or the audit pack, like the level.

For the owner

Recommendation: direction A, Tiles — with B's table as its list mode one click away, and the project summary on the server. It is the only direction that makes each program a living object (its map, its score, its decision, where it stands in both products) and shows the portfolio at a glance, and it is fast once the summary exists. If 3.5.0 has no room: ship the two-product wording and the new-account pair (step 1 below) in 3.5.0 and the tiles in 3.5.1.

Decisions

  1. W1 Product names: "Analyse" and "Re-design" (recommended: the landing CTA already says "Analyse your own Z program", and Analyze's ending card says "Re-design this program"), or "Understand" / "Rebuild" — but "Rebuild" is already one of the four decision options (Keep, Rebuild, Move to SAP standard, Retire), so it would mean two things. "Modernise" is vaguer. Tool names stay (Analyze, Design … Delivery).
  2. W2 Spelling: the tool is "Analyze" (US, PHASES), the product verb "Analyse" (UK, landing and own-code copy). Keep both as today, or align the tool to "Analyse" (touches every guard that names it). Recommended: keep, the product word is a verb and the tool a name.
  3. W3 Re-design without "optional": both products as equal cards for a new account; for a returning account each program shows both lines with an action each. Agreed?
  4. W4 How Re-design starts: honest version proposed — "Re-design starts from an analysis, so the evidence is there first". Two starts: "Re-design an example end to end" (runs the analysis of Z_MM_PO_APPROVAL — free the first time — and opens Design instead of Analyze), and "Re-design a program" for an analysed one. The intent travels in the same session handoff as the own-code start, no stored field.
  5. W5 When the decision is not Rebuild: Keep, Move to SAP standard and Retire build nothing. Recommended: the Re-design line then says "Not needed — decided: Retire" and offers "Open the decision", instead of pushing a re-design.
  6. W6 Header: no own header entry for Re-design (recommended — the header holds places, not products; both products start from My workspace and from each program). Alternative: "Re-design" as a filter link in the header.
  7. W7 Landing: the landing's two CTAs ("Watch the 4-minute demo", "Analyse your own Z program — free account") stay; the landing's product section names the same two products with the same words, and after the demo the H2 banner here continues it ("You have seen Z_MM_PO_APPROVAL…").
  8. W8 Cost per product: Analyse: "1 analysis run per program, 5 free, examples free the first time, the same code again free" (lib/run-quota-rule.ts, reserveRunQuota). Re-design: "Not counted against your runs" — the six tools are unmetered (lib/constants.ts). Say both on the cards, as drawn.
  9. W9 Lenses: "Read as Business · IT · Management" only highlights one of the three facts per tile and opens the program in that view. Remembered per browser, never stored. Agreed, or no lens on this page at all?
  10. W10 KPIs: five count tiles from the project list, shown from three programs on; they are the filter (no second filter bar). "Changed in the last 7 days" instead of "since your last visit" (no account field).
  11. W11 Project summary on the server (Data and speed panel): agreed as a project-level, Admin-SDK-only field set, outside the signed run?
  12. W12 Release slot (below).

New visual elements (derived from existing ones)

  • Program tile — a CcCard with the object identifier, a thumbnail and two status rows built from ProjectProgressCell.
  • Map thumbnail — the map's geometry in our map ink and surface tokens; no labels (names need the full map).
  • Re-design track — six segments, the same segment logic as the old stepper, ink for done, ring for the current step, green only when the delivery is signed.
  • Count tile — a pressable card with one figure (the score's hero style, 28 px instead of 64).
  • Product mark — micro label + 16 px lucide icon (workflow for Analyse, wrench for Re-design), same shape for both.
