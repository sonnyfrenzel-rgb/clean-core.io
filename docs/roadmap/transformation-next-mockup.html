          What is wrong today

          • The view switch changes nothing. StageHeader carries Business · IT · Management on every tool (components/StageHeader.tsx:54–57, StageViewSwitch.tsx). Transformation reads the view only to keep it in its links (transformation/page.tsx:399, lib/transformation-chain.ts:118–119, 206–212); TransformationObjectPage.tsx has no view at all. A manager and a developer get the same page while the header promises them different ones.
          • There is no answer, only figures. The first screen is four facets with four different units — objects, findings with a target option, successors, unticked checklist items (TransformationObjectPage.tsx:373–447) — and a status line of five dot items (449–474). No sentence says what the program became, into which extension type, or what to do next. The target appears only as the word "ABAP Cloud (RAP)" in a facet's unit (378) and in the header lead.
          • "19 of 19 planned" though 9 have no target. The facet "Plan from the engine" counts findings with any targetOptions (lib/transformation-view.ts:157). Every finding of the starter example has options, so it reads 19 of 19, "0 left out — every finding has a target option" (TransformationObjectPage.tsx:396–400) — while 4 have no released successor and 5 are custom tables whose new home nobody decided (transformationFlow, measured). The facet sounds like "done" for a page that is half open.
          • Up to ten strips stand above the answer. Prerequisites (page.tsx:2299), the stale notice (2326), the quality tips (2332), copy failed (2340), contract refusal (2354), error (2363), cancelled (2380), unsaved draft (2388), hard-coded values (2403), code checks (2421) — and then the "Built on" card (2449) with its own strips for not-written functions and abaplint (BuiltOnCard.tsx:74–96). The result of the checks is a warning strip above the facets, the abaplint verdict a strip inside a card; neither is counted anywhere in the header.
          • The checklist is a headline. "Grounding audit — N not ticked yet" is one of the four facets (TransformationObjectPage.tsx:432–446), though it is a personal list kept in this browser only and not a step of the code's status (the side column says so itself, 663–665).
          • Three sections tell the same story. The flow "From your code to the generated package" (486–492), "From finding to change" with 3 rows and "Show all 19" (577–600, FIRST_CHANGES = 3 at 331) and "Plan by kind" (602–638) all count findings by kind and target; "Plan by kind" repeats the flow's left column.
          • The third box is a text search. "Generated change" finds a file that merely names the object (changeExcerpt, lib/transformation-view.ts:285–307) and says so ("a place to look, not proof", TransformationObjectPage.tsx:273) — though since ADR-101 the package carries traceability.json with each function's ABAP lines, the exact answer.
          • The code is at the foot. "Side by side with ABAP" is a full-width section under everything (after, TransformationObjectPage.tsx:718; page.tsx:2021), reached by a button in the package header; a function in the package cannot open its own code.
          • Technical words in the bar. The anchors are "Code to package · Generated package · Finding to change · Plan by kind · Side by side" (lib/page-anchors.ts:125–135), drawn by the old bar style.

          • "Not generated, and why" (notGeneratedReasons) — its texts are quoted unchanged in the side column.
          • Author per object (engine / bodies by the model), the 3.0.23 rule that "Code generated" is not ticked while the tool bar says "not activatable", and the check words of lib/transformation/check-words.ts (passed / failed / not run, who ran it).
          • The generation screen (GenerationChain) and the "Before the run" tips — kept, moved into the same header.
          • The demo writes no code: "The demo stops where the model begins."

          For the owner — decisions T1–T13

          Recommendation: build T2–T11 as one Transformation step of the tools release, on one page for every reader (T1, decided). The page opens with what the program became, its target, how much of it has a released target, whether the code is written and whether the checks passed — and the one next step. Everything a developer needs stays on the page, quietly: the flow on a click, the package with its functions, the checks with who ran them, the trace folded, the code in a drawer. No engine change, no new stored field, no rules change.
          1. T1 One page for every reader — decided (Sonny, 15.11.2026: one view for everyone, "dafür noch schicker und für alle tauglicher"; refined the same day: "das verwirrt nur"). Transformation has no Business, IT or Management variant, and the header shows no view switch on this tool — desktop and phone. In its place a quiet note: "One page for every reader — business, IT and management". The view stays in the address so the way back returns to the view the reader came from. Same rule as Economics (E7) and Documentation.
          2. T2 The answer first. Object page header: the question "What became of <program>?", one or two sentences, the next step on the right, and four facets — Target (extension type and level it aims at), Released target (findings with a released API or handled by RAP), Code written (functions, who wrote them), Checks (passed / failed / not run). Each state of the tool writes its own answer (generated, generating, nothing yet, a check failed, demo). Recommended.
          3. T3 Count targets, not options. "Released target" counts findings whose target is a released successor or the project route; custom tables and calls without a released successor are "open", never "planned". Replaces "Plan from the engine: 19 of 19". The side column's status gains "Checked here" (abaplint) and keeps "Activated" and "Tested" as not done here. Pure change in lib/transformation-view.ts. Recommended.
          4. T4 Strips only for what stops the page. Generation error, contract refusal, unsaved draft and the stale notice stay above the header (they change what the page means). Hard-coded values, code lints, not-written functions and the abaplint verdict become rows of Checks and are counted in the Checks facet; the answer names a failure in its first sentence. Recommended.
          5. T5 One flow: finding → target → object. The flow's third column names the objects of the package (logic class, behavior pool, port interface, "not in the package") from traceability.json instead of one "package" box; choosing a target lists its findings with their lines. "From finding to change" and "Plan by kind" go. On a phone the flow is a grouped list. Recommended.
          6. T6 "Still open" — one list. Custom tables without a home, calls without a released successor, output that becomes a Fiori app, constructs the engine did not assess, rules without a decision — each one line with one action (Design, Analyze, Business view). The same items as the project's open questions (ADR-081), filtered to what touches this code. Recommended.
          7. T7 Package by object, code in a drawer. Objects with author chips; open one for its functions (ABAP lines, rule ids, who wrote the body, status) and its files; "Code" opens a drawer with the old ABAP and the new function side by side, engine-written lines and AI-written lines marked in the gutter. "Side by side with ABAP" as a section at the foot goes. Recommended.
          8. T8 Checks as one table. abaplint (server), body guards, code lints, hard-coded values, abapGit formats (this browser), ABAP Unit and activation (not run here — your system), and "Check by hand" (the grounding audit, this browser only). The grounding audit leaves the facet row. Recommended.
          9. T9 "Finding by finding" from the trace, folded. All 19 findings with their places, target, how sure, level, and the function that now carries each — from traceability.json, not a text search. Closed by default. Recommended.
          10. T10 The shared "On this page" bar (tmp/ANCHOR-BAR-SPEC.md): Where findings went · Still open (amber count) · The package · Checks · Finding by finding. Amends ADR-091's Transformation list. Recommended.
          11. T11 Generating in the same page. While the code is written the header answers "Writing the code — 13 of 22 functions", the facets update, Cancel is the next step; the generation screen's "what it builds on" moves into the side column's "Built on". Recommended; alternative: keep today's full-screen GenerationChain.
          12. T12 Tool bar order — decided (Sonny, 15.11.2026): Analyze → Economics → Design → Transformation → Documentation → Testing → Delivery. Shown here; built in lib/workflow-steps.ts with the Economics step, not by this one.
          13. T13 Level wording. The Target facet says "aims at clean core level A" and counts how much of the code has a released target, never "the package is level A": a level belongs to objects SAP's classification names, and the 9 open findings are not graded until decided. Recommended.
